# 심사위원 설계

실제 심사에서 중요한 질문은 **누가 이 글을 읽는가**다. 해커톤의 주최는 회사지만, 서류는 운영진이 보고 본선은 외부 VC나 현업 개발자가 볼 수 있다. 페르소나는 주최 기관이 아니라 **이 글을 실제로 읽는 단계의 심사자**를 기준으로 만든다.

두 가지를 알고 쓴다.
- **LLM 심사위원은 LLM이 쓴 글에 관대하다.** 자기 글을 알아보고 더 높게 평가한다. 이력서 실험에서는 같은 모델로 쓴 지원자가 더 많이 통과했다. Claude가 쓴 초안을 Claude가 심사하면 이 편향이 그대로 들어간다. 그래서 다른 회사 모델을 함께 쓰고, 집계할 때 모델 계열을 구분한다.
- **페르소나 심사는 실제 심사의 대리 지표다.** 사람 심사자끼리도 점수가 잘 맞지 않는다. 그래서 총점보다 **같은 지적이 반복되는지**를 본다.

## 1. 심사 단계 정하기

`research/A.md`의 심사 구조를 보고 이 글이 읽히는 단계를 정한다. 지원서 대부분은 서류 단계다.
- 서류 심사를 누가 하는지 공개돼 있으면 그대로 쓴다.
- 공개돼 있지 않으면 아래 유형별 기본값을 쓰고, 브리핑에 "가정"이라고 표시한다.
- 실제 심사위원 명단이 있으면 그 사람들의 **역할과 배경**(예: "시리즈 A 투자사 파트너, 핀테크 투자 이력")으로 페르소나를 만든다. 이름을 쓰거나 말투를 흉내 내지 않는다.

## 2. 페르소나 3명 (`judges.md`)

세 명이다. 같은 역할을 여러 명에게 주면 한 명과 다를 게 없었다. 서로 **보는 기준**이 달라야 한다.
- **1번 핵심 심사자**: 이 단계에서 통과 여부를 실제로 정하는 사람. 가장 무게가 크다.
- **2번 전문가**: 내용의 깊이와 실현 가능성을 보는 사람.
- **3번 결정권자 또는 외부인**: 기억에 남는지, 다른 지원자와 다른지, 면접에서 이 글을 믿을 수 있을지를 보는 사람.

### 유형별 기본값

| 유형 | 1번 핵심 심사자 | 2번 전문가 | 3번 결정권자·외부 |
|---|---|---|---|
| 해커톤·공모전(서류) | 운영진: 완주할 사람인가, 팀에 보탬이 되나, 성실하게 썼나 | 기술·도메인 심사위원: 문제 정의, 실현 가능성 | 후원사·투자자: 임팩트, 차별성 |
| 해커톤·공모전(본선 기획서) | 외부 심사위원(배점표 기준) | 기술 심사위원 | 후원사·투자자 |
| 인턴십·채용 | 인사담당자: 문항 충족, 위험 신호, 직무 관련 경험 | 현업 팀장: 직무 이해, 역량 근거 | 임원: 기억에 남나, 조직에 맞나 |
| 교육 프로그램·대외활동 | 운영 담당자: 참여 의지, 끝까지 할 사람인가 | 강사·멘토: 배울 준비가 됐나, 수준이 맞나 | 선배 수료생: 이 프로그램을 제대로 이해했나 |
| 장학금 | 운영위원: 자격, 필요성 | 교수·전문가: 학업·연구 계획의 깊이 | 재단 관계자: 재단 취지와 맞나 |
| 지원사업·투자 | 평가위원: 배점표를 기계적으로 채점 | 산업 전문가: 시장과 기술 | 투자자: 팀, 성장성 |

### `judges.md` 형식

```markdown
심사 단계: <서류 / 본선 …> (근거: <research/A.md 인용> 또는 "가정")
배점표: <공고 원문, 없으면 "명시 없음 → 공통 기준 사용">

## 1번 <역할> (핵심 심사자)
- 배경: <누구인지, 오늘 지원서를 몇 편이나 읽는지>
- 중요하게 보는 것: <2~3개>
- 바로 감점하는 것: <2~3개>

## 2번 <역할>
...

## 3번 <역할>
...
```

### 공통 기준 (배점표가 없을 때)

총점을 바로 매기면 흔들린다. 기준을 예/아니오 질문으로 쪼개면 심사자끼리의 일치도가 크게 올랐다. 그래서 항목마다 질문에 답한 뒤, "예"의 비율로 점수를 낸다.

| 항목(배점) | 예/아니오 질문 |
|---|---|
| 문항 충족 (30) | 문항의 요구를 모두 답했나 / 공고의 선발 기준과 이어지나 / 묻지 않은 얘기로 분량을 쓰지 않았나 |
| 구체성·근거 (30) | 본인이 한 행동이 동사로 나오나 / 숫자·고유명사·장면이 있나 / 왜 그렇게 했는지와 다른 선택지가 나오나 |
| 적합성 (20) | 이 프로그램만의 특정 사실과 이어지나 / 기대가 프로그램이 주는 것과 맞나 |
| 차별성 (20) | 다른 지원자와 바꿔도 되는 문장이 없나 / 읽고 나서 기억나는 한 문장이 있나 |

배점표가 공개돼 있으면 그 항목을 같은 방식으로 예/아니오 질문 2~3개로 쪼갠다.

## 3. 심사 자료 (`review/pack.md`)

넣는 것:
- 프로그램 소개(공고에 공개된 것, 다섯 줄 이내)
- 공개된 심사 기준과 배점표
- 문항 원문, 안내 문구, 분량
- 지원서 전체(모든 문항의 `draft/q*.md`)

넣지 않는 것: `material.md`, 인터뷰 기록, `briefing.md`, 조사의 연결고리·추론. 실제 심사위원은 이런 걸 모른다.

**외부 심사위원용 사본** (`review/pack-ext.md`): `config.md`에서 `mask_personal_info: yes`면 사용자 이름, 연락처, 학번, 주소를 `[이름]`, `[연락처]`처럼 가린다. 학교나 회사 이름은 글 내용에 필요하면 그대로 둔다.

## 4. Claude 심사위원 프롬프트 (Agent, `model: "sonnet"`, 3명 병렬)

```
너는 <judges.md의 N번 역할과 배경>이다.
중요하게 보는 것: <…> / 바로 감점하는 것: <…>

<review/pack.md 경로>를 읽고 이 지원서를 심사해. 다른 파일은 읽지 마.
이 글은 지원자 본인이 직접 썼다. 오늘 비슷한 지원서를 많이 읽었다는 걸 기억해.
칭찬으로 시작하지 말고, 예의를 차리느라 점수를 올리지 마. 길이나 문장 솜씨로 가점하지 마.

먼저 각 문항의 첫 단락만 읽고 3번 첫인상을 정한 뒤, 전체를 읽어.
결과를 <작업폴더>/review/claude-<N>.md 에 아래 형식으로 쓰고(400단어 이내), 나에게는 점수와 9번만 한 줄로 돌려줘.

1. 점수: <배점표 또는 공통 기준>의 예/아니오 질문에 하나씩 답하고(아니오면 이유 한 구절), 항목별 점수와 총점
2. 판단: 통과 / 보류 / 탈락
3. 첫인상: 첫 단락만 읽고 계속 읽고 싶었나, 한 줄
4. 기억에 남는 것: 이 지원자에 대해 기억나는 것 한 문장. 없으면 "없음"
5. 누구나 쓸 수 있는 문장: 다른 지원자와 바꿔도 말이 되거나 상투적인 문장. 원문 인용 (최대 3개)
6. 궁금한 것: 글에 없어서 더 알고 싶은 것. 면접이라면 할 질문 (최대 3개)
7. 믿기 어려운 곳: 면접에서 물으면 지원자가 설명하기 어려울 것 같은 문장. 원문 인용과 이유 (최대 3개)
8. 문항별로 답하지 않은 요구
9. 가장 먼저 고칠 것 하나
```

여러 문항이나 여러 버전을 심사할 때는 심사위원마다 문항 순서를 섞는다. 순서에 따라 판단이 달라진다. 버전끼리 비교할 때도 "A와 B 중 뭐가 낫나"로 묻지 않고 각각 따로 심사한 뒤 비교한다. 쌍대 비교는 판정이 쉽게 뒤집힌다.

## 5. 외부 심사위원 (Codex, Antigravity)

다른 회사 모델은 Claude가 쓴 문장에 대한 자기선호가 없다. 서로 다른 계열 모델로 꾸린 패널이 한 모델 단독보다 사람 판정과 더 잘 맞았다.
- **Codex**: 1번 핵심 심사자 페르소나를 그대로 맡는다. 같은 사람을 다른 모델이 보게 해서 교차 확인한다.
- **Antigravity (Gemini)**: 배점표 기준 종합 심사위원. 5번 "누구나 쓸 수 있는 문장"을 특히 엄격하게 본다.

프롬프트는 위와 같다. 다른 점은 세 가지다. `pack-ext.md` 내용을 프롬프트 안에 붙이고, 결과는 응답으로 출력하게 하고, 형식은 1~9번 그대로다. `review/prompt-codex.md`, `review/prompt-agy.md`로 저장한 뒤, Claude 심사위원과 같은 메시지에서 Bash 백그라운드로 실행한다.

```bash
bash <skill-dir>/scripts/run_judge.sh codex <작업폴더>/review/prompt-codex.md <작업폴더>/review/codex.md
bash <skill-dir>/scripts/run_judge.sh agy   <작업폴더>/review/prompt-agy.md   <작업폴더>/review/agy.md
```

실패하면(설치 안 됨, 로그인 만료, 시간 초과) 출력 파일에 `[실패] 이유`가 남는다. 그 심사위원은 빼고 취합하고 사용자에게 한 줄로 알린다(예: "Antigravity 로그인이 만료돼서 빠졌어요. 터미널에서 `agy`를 한 번 실행해 로그인해 주세요").

## 6. 취합 (`review/summary.md`, 메인)

```markdown
| 심사위원 | 모델 | 점수 | 판단 | 고칠 것 1순위 |
|---|---|---|---|---|
| 1 운영진 | Claude Sonnet | 72 | 보류 | … |
| 1 운영진 (교차) | Codex | 65 | 보류 | … |
| 2 기술 심사 | Claude Sonnet | … | … | … |
| 3 후원사 | Claude Sonnet | … | … | … |
| 종합 | Gemini | … | … | … |

Claude 평균 <점수> / 외부 평균 <점수>

## 다른 모델 계열이 같이 지적한 것 (먼저 고친다)
## 핵심 심사자(1번)가 지적한 것
## Claude 심사위원끼리만 겹친 것
## 의견이 갈린 것 (사용자가 판단)
## 사용자에게 물어볼 것 (6번 '궁금한 것'에서)
```

- 같은 문장이나 같은 문제를 **서로 다른 계열(Claude와 GPT, Claude와 Gemini)**이 짚었으면 맨 위에 둔다. Claude 페르소나 세 명이 겹친 것은 한 모델의 판단이 반복된 것일 수 있어서 그 아래에 둔다.
- 외부 심사위원이 없으면 "같은 모델 안의 합의라 Claude에 관대할 수 있어요"라고 한 줄 알린다.
- Claude 평균이 외부 평균보다 10점 넘게 높으면 그 차이를 알린다.
- 심사위원 원문을 다 붙이지 않는다. 사용자에게는 표와 각 절의 핵심만 보여 준다.

## 7. 재심사

사용자가 원할 때만 한다. 총점이 가장 낮았던 심사위원 1명을 새로 띄워 고친 버전을 심사한다(외부 심사위원이었으면 같은 스크립트로). 이전 심사 결과는 보여 주지 않는다. 심사는 최대 2라운드이고, `state.md`에 라운드를 기록한다.

## `~/.claude/write-with-me/config.md` 형식

```
external_judges: 미확인        # 미확인 | 없음 | codex | agy | codex, agy
codex_model: 기본값             # 기본값이면 ~/.codex/config.toml의 model을 쓴다
codex_reasoning: medium
agy_model: gemini-4-neon-medium # agy models 로 목록 확인. Claude 계열은 고르지 않는다
mask_personal_info: yes
```
