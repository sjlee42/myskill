# 조사 브리프

1단계에서 Agent 도구(general-purpose)로 **한 메시지에서 병렬 실행**한다. 모델은 SKILL.md 표대로 쓴다. `<>`를 채운다.

세 브리프는 범위가 겹치지 않게 나눴다. 공고와 심사 구조는 A, 조직과 인재상은 B, 지난 사례와 심사평은 C가 맡는다. 사용자 개인정보(이름, 학교, 연락처)는 넣지 않는다.

**공통 꼬리말** (세 브리프 끝에 모두 붙인다):

```
규칙:
- 결과는 <작업폴더>/research/<A|B|C>.md 에 한국어로 쓴다. 500단어 이내.
- 직접 열어 본 페이지에서만 인용한다. 인용문은 원문 그대로, 바로 뒤에 출처 URL.
- 확인 못 한 항목은 추측하지 말고 "확인 못 함"이라고 적는다. 로그인이 필요하거나 열리지 않은 페이지는 URL과 함께 "접근 불가"로 적는다.
- 파일을 쓴 뒤, 나에게는 10줄 이내 요약만 돌려준다: 찾은 것 핵심, 못 찾은 것, 파일 경로.
```

## A. 공고와 심사 구조 (haiku)

```
<대상>의 <프로그램명>(<연도/기수>) 모집 공고를 조사해 줘. 지원서를 쓰려는 사람을 돕는 조사다.
공고 원문: <brief.md 경로 또는 URL, 없으면 "직접 찾을 것">

찾을 것:
1. 공고 URL, 모집 기간, 마감 시각, 전형 일정(서류·면접·본선·활동 기간), 선발 인원, 자격, 혜택
2. 지원서 문항 전체 원문, 문항별 분량과 기준(공백 포함/제외), 문항 옆 안내 문구. 한 글자도 바꾸지 말 것
3. 심사 구조: 전형 단계별로 누가 심사하는가(운영진, 현업, 외부 심사위원, 후원사 등). 공개된 심사위원 명단과 각자의 소속·배경
4. 심사 기준과 배점표(명시된 경우 원문). 없으면 "명시 없음"
5. FAQ, Q&A, 설명회에서 지원서와 관련된 내용
6. 지원서 작성 규정: AI 사용 금지·허용 범위, 타인의 대리 작성·편집 금지, 받은 도움이나 AI 사용 신고 의무, 블라인드 채용 여부(출신지·학교·가족 기재 금지). 원문 그대로. 없으면 "명시 없음"
```

## B. 조직 (sonnet)

```
<대상>이 어떤 곳인지 조사해 줘. <프로그램명>(<URL>)에 지원서를 쓰려는 사람을 돕는 조사다. 공고 내용 자체는 다른 조사가 맡으니 조직에 집중해.

찾을 것:
1. 무엇을 하는 곳인가: 핵심 제품·서비스, 고객, 규모 (세 줄)
2. 스스로 밝힌 미션, 인재상, 일하는 방식 (원문 인용)
3. 최근 6개월 주요 소식 중 이 프로그램과 관련될 만한 것 (출시, 투자, 행사, 리더 인터뷰)
4. 이 프로그램을 여는 이유로 보이는 것 (채용 연계, 생태계, 브랜딩 등)과 근거
5. 프로그램 운영자나 담당 조직이 공개적으로 한 말 (블로그, SNS, 인터뷰)
```

## C. 지난 사례와 심사평 (sonnet)

```
<대상>의 <프로그램명>(<URL>) 이전 기수, 또는 같은 조직의 비슷한 과거 프로그램을 조사해 줘. 지원서를 쓰려는 사람을 돕는 조사다.

찾을 것:
1. 이전 참가자·합격자 후기 중 지원서, 면접, 선발에 대해 말한 부분 (블로그, 브런치, 링크드인, 커뮤니티)
2. 이전 수상작이나 결과물: 어떤 아이디어와 어떤 사람이 뽑혔나
3. 이전 심사위원 구성과 공개된 심사평·총평 (무엇을 칭찬하고 무엇을 아쉬워했나)
4. 후기들에서 반복되는 포인트
5. 비슷한 다른 프로그램과 비교한 이 프로그램만의 특징
이전 기수 정보가 없으면 그렇다고 적는다.
```

## 작은 공모전일 때 (B+C 합본, sonnet 1개)

정보가 적으면 B와 C의 "찾을 것"을 합쳐 에이전트 하나로 돌린다. 결과 파일 이름은 `research/BC.md`로 한다.

## 결과 쓰는 법

메인은 세 파일을 합쳐 다시 쓰지 않는다. 바로 `briefing.md`와 `judges.md`를 만든다. 같은 내용을 여러 번 옮겨 적지 않기 위해서다. 브리핑의 "찾는 사람"에는 두 파일 이상에서 확인된 것을 먼저 쓴다.
