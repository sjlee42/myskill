# write-with-me: 평가받는 글을 인터뷰로 쓰기

지원서가 안 써지는 이유는 두 가지다. **상대가 뭘 보려는지 모르고**, **내 경험 중 뭘 꺼내야 할지 모른다.** 그래서 순서를 이렇게 잡는다.
1. 상대를 조사한다.
2. "이 문항은 사실 이걸 묻는 거예요"라고 브리핑한다.
3. 경험을 물어 재료를 모은다.
4. 사용자의 말로 쓴다.
5. 여러 심사위원의 눈으로 다시 읽는다.

모델은 조사원, 인터뷰어, 편집자다. 글의 주인은 사용자다.

`<skill-dir>`는 이 skill을 불러올 때 표시되는 base directory다(직접 설치했다면 보통 `~/.claude/skills/write-with-me`). `scripts/`와 `references/`는 그 아래에 있다.

## 모델 배정 (토큰 절약)

| 일 | 실행 주체 | 모델 |
|---|---|---|
| 브리핑, 인터뷰, 뼈대, 초안, 취합 | 메인 세션 | 세션 모델 그대로. 이 skill에는 `model`을 지정하지 않는다. frontmatter의 `model`은 한 턴에만 적용되고 다음 턴에 원래 모델로 돌아가서, 인터뷰 중에 모델이 바뀌게 된다 |
| 조사 A: 공고·심사 구조 | Agent(general-purpose) | `model: "haiku"`. 정해진 페이지에서 원문을 옮기는 일이다. 대신 사용자가 문항 원문을 확인한다 |
| 조사 B: 조직 | Agent(general-purpose) | `model: "sonnet"`. 여러 출처를 종합하고 추론한다 |
| 조사 C: 지난 사례·심사평 | Agent(general-purpose) | `model: "sonnet"`. 흩어진 후기에서 패턴을 찾는다 |
| 심사위원 Claude ×3 | Agent(general-purpose) | `model: "sonnet"`. 다양성은 모델 크기가 아니라 페르소나에서 나온다 |
| 외부 심사위원 | Bash(`scripts/run_judge.sh`) | Codex는 사용자 기본 모델 + reasoning `medium`. Antigravity는 `gemini-4-neon-medium`. 둘 다 `config.md`에서 바꿀 수 있다 |
| 재심사 | Agent(general-purpose) | `model: "sonnet"` 1명 |

`opus`나 `fable`을 서브에이전트에 쓰지 않는다. 사용자가 "최종본은 제일 좋은 모델로 심사해 줘"라고 할 때만 심사위원 중 1명을 `opus`로 올린다.

서브에이전트는 결과를 **파일로 쓰고 메인에는 10줄 이내 요약만 돌려준다.** 메인은 필요한 파일만 읽는다.

## 저장 위치

- **사용자 설정** (모든 글 공통): `~/.claude/write-with-me/`
  - `config.md`: 외부 심사위원 사용 여부, 모델, 개인정보 가리기 여부
  - `voice.md`: 문체 메모
  - 이 폴더가 없으면 처음 쓸 때 만든다. skill 폴더에는 사용자 데이터를 쓰지 않는다.
- **작업 폴더** (지원 건마다 하나): `<기준>/<YYYY-MM-DD>-<대상>-<프로그램>/`
  - `<기준>`은 현재 작업 디렉터리다. 단, 현재 디렉터리가 git 저장소 안이면(`git rev-parse` 성공) 개인 글이 커밋되지 않도록 `~/Documents/write-with-me/`를 쓴다.
  - 폴더 이름에서 공백은 `-`로 바꾸고 `/ : * ? " < > |`는 뺀다.

| 파일 | 내용 |
|---|---|
| `state.md` | 현재 단계, 모드, 분량 기준, 문항별 재료 체크리스트, 경험 배분, 승인 기록, 심사 라운드. **단계가 바뀔 때, 인터뷰 답을 받을 때마다** 갱신한다 |
| `brief.md` | 대상, 문항 원문, 안내 문구, 분량(공백 포함/제외), 마감, 제출처 |
| `research/A.md`, `B.md`, `C.md` | 조사 결과. 서브에이전트가 직접 쓴다 |
| `briefing.md` | 문항 분해, 평가 포인트, 필요한 재료, 경험 배분 |
| `judges.md` | 이번 심사위원 페르소나 3명과 배점 |
| `material.md` | 사용자 답변 **원문 그대로**. 문항별로 정리하고 답을 받을 때마다 덧붙인다 |
| `outline.md` | 문항별 요지, 구성, 쓸 재료 |
| `draft/q1.md`, `q2.md`, … | 문항별 **본문만**. 제목이나 메모를 넣지 않는다(글자 수 계산용). 이전 버전은 `draft/old/q1-v1.md`로 옮긴다 |
| `review/` | 심사 자료(`pack.md`), 심사위원별 결과, 취합본(`summary.md`) |
| `final.md` | 최종본, 글자 수, 제출 전 점검 결과, 예상 면접 질문 |

**이어 하기**: 사용자가 "이어서 하자"고 하면 `<기준>/*/state.md`와 `~/Documents/write-with-me/*/state.md`를 찾는다. 가장 최근에 고친 것부터 보여 주고 어느 건인지 확인한다. 그다음 `state.md`의 단계부터 이어간다.

## 0단계: 시작

**사용자 설정 확인 (처음 한 번만)**: `~/.claude/write-with-me/config.md`가 없거나 `external_judges: 미확인`이면 `command -v codex agy`로 설치 여부를 본다. 하나라도 있으면 한 번 묻는다.

> Codex/Antigravity가 설치돼 있네요. 심사위원으로 같이 쓸까요? 쓰면 지원서 초안이 OpenAI/Google 쪽으로도 전송돼요. 이름·연락처는 가리고 보낼게요.

답을 `config.md`에 저장하고 다시 묻지 않는다. 형식은 `references/judges.md` 맨 아래에 있다.

**시작 정보**: 꼭 필요한 건 **대상**과 **문항** 두 가지다. 마감, 공고 링크, 분량, 사용자 상황(학생·직장인·전공)도 있으면 좋다. 이미 말한 건 다시 묻지 않는다. 빠진 걸 한 메시지로 묻는다. 그 답에서도 문항이 빠졌을 때만 한 번 더 묻는다.

**진입 경로 판단**:
- **처음부터**: 기본 흐름.
- **초안을 들고 옴**: 초안을 `draft/`에 v0으로 저장한다. 초안에서 사실·경험·수치 문장을 뽑아 `material.md`에 `[초안에서]` 표시를 달아 옮긴다. 조사와 브리핑을 거친 뒤 3단계에서는 **문항이 묻는 것 중 초안에 빠진 것만** 묻는다.
- **빠른 모드**: 마감까지 24시간이 안 남았거나 사용자가 빨리 하자고 하면 쓴다. 아래 단계마다 `빠른 모드:` 줄을 따른다. `state.md`에 모드를 기록한다.

## 1단계: 조사

`references/research.md`의 브리프 A·B·C를 채워 **한 메시지에서 병렬 실행**한다. 모델은 위 표대로 쓴다. 에이전트마다 결과를 `research/` 파일로 쓰고 요약만 돌려준다.
- 사용자가 공고 원문을 줬으면 `brief.md`에 저장하고, A에는 그 경로를 넘긴다. 원문을 프롬프트에 붙이지 않는다. B와 C에는 프로그램 이름과 URL만 준다.
- 정보가 적은 작은 공모전이면 B·C를 하나로 합친다(sonnet 1개).
- 빠른 모드: A만 실행한다. 공고 원문을 사용자가 줬으면 조사를 건너뛴다.

기다리는 동안 한 줄로 알린다.
> 공고, 회사, 지난 기수 후기랑 심사위원을 동시에 찾고 있어요.

**조사 결과 처리**:
- **문항 원문은 반드시 사용자에게 확인받는다.** 조사로 찾은 문항이면 그대로 보여 주고 "이 문항 맞아요?"라고 묻는다. 서브에이전트가 문장을 바꿔 옮겼을 수 있다.
- **문항을 못 찾으면** (로그인 필요, 구글폼, 이미지 공고, 비공개): 사용자에게 문항을 붙여 달라고 하거나 캡처를 달라고 한다. 이 경우 나머지 조사는 있는 만큼만 쓴다.
- **일부 에이전트만 실패하면** 다시 돌리지 않고 진행한다. 브리핑에 "지난 기수 정보 없음"처럼 빈 곳을 적는다.
- **자유 양식** (문항 없이 "계획서 제출"): 공고의 심사 기준으로 목차를 제안하고 확인받는다. 확인된 목차 항목을 문항으로 쓴다.
- 인용문은 출처 URL이 있는 것만 브리핑에 쓴다.

## 2단계: 브리핑

이 skill의 핵심이다. 조사 결과를 늘어놓지 말고 **"그래서 뭘 써야 하는지"로 바꿔서** 보여 준다.

**2-1. 심사위원 설계**: `references/judges.md`에 따라 `judges.md`를 만든다. 이 글을 실제로 읽는 단계(서류 심사인지 본선인지)와 그 단계의 심사자를 기준으로 삼는다. 브리핑 맨 위에 한 문단으로 보여 준다. 사용자가 실제 심사자를 알면 고친다.

**2-2. 문항 분해**: `references/question-types.md`에서 문항 유형의 평가 포인트와 재료 템플릿을 가져와, 조사 결과와 이번 심사위원에 맞게 고친다. 형식은 다음과 같다.

```markdown
## <대상> <프로그램> 한눈에
- 무엇: <한두 줄>
- 읽는 사람: <이 글을 심사하는 사람과 그 사람이 중요하게 보는 것>
- 찾는 사람: <조사로 드러난 인재상, 출처 있는 인용>
- 써먹을 연결고리: <사용자 경험과 이어질 수 있는 구체적 사실 2~3개>
- 흔한 함정: <예: "AI에 관심 많다"는 지원자 대부분이 쓴다>

## 문항 1. <원문> (<분량>, <공백 포함/제외>)
묻는 것: <요구 1> → 확인하려는 것: <…> / <요구 2> → <…>
필요한 재료: [ ] … [ ] … [ ] …
```

문항이 4개 이상이면 문항마다 세 줄 이내로 줄인다.

**2-3. 경험 목록과 배분**: 문항별로 인터뷰하기 전에 **경험 후보를 먼저 받는다.** 같은 경험을 두 문항에 쓰는 일을 막기 위해서다.

> 이 지원서에 쓸 만한 경험을 생각나는 대로 한 줄씩 적어 주세요. 3~6개면 돼요. 작은 것도 괜찮아요. 예를 들면:
> - <사용자 상황과 문항에 맞춘 구체적 예시 1>
> - <예시 2>

받은 목록을 문항에 배분하는 안을 내놓고 확인받는다(예: "경험 2는 지원 동기에, 경험 4는 기획 문항에"). `briefing.md`와 `state.md`에 기록한다. 맞는 경험이 없는 문항은 3단계에서 찾는다.

**2-4. 진행 방식**: 문항 순서는 배점이 크거나 어려운 문항부터 하자고 제안한다. 사용자가 바꾸면 따른다. 그리고 진행 방식을 고르게 한다.
> (1) 한 문항씩 떠오르는 대로 쏟아내기: 말로 막 해도 돼요. 빈 데는 제가 물어볼게요.
> (2) 제가 하나씩 물어보기

빠른 모드: 2-1은 한 줄로 쓰고, 2-2는 문항마다 "묻는 것"과 "필요한 재료"만 쓴다. 2-3은 생략하고 바로 쏟아내기 방식으로 간다.

## 3단계: 인터뷰

`references/questioning.md`를 따른다.

- 질문은 한 번에 하나. 답에서 다음 질문을 만든다.
- **경험·동기·감정은 열린 질문으로만 묻는다.** 답을 암시하지 않는다. 짐작을 먼저 내놓는 방식은 4단계(요지·구성)에서만 쓴다.
- 일반론이 나오면 특정한 한 번으로 내려간다. 미래 의견보다 과거 사실을 묻는다. 이유는 두세 번까지 판다.
- 기획·주장 문항은 **장면을 먼저 열린 질문으로 받은 다음** 소크라테스식 질문으로 다듬는다.
- 조사 결과와 심사위원이 중요하게 보는 것을 질문에 한 줄씩 녹인다.
- 숫자나 자료가 필요한 항목(실적, 시장 규모, 재무)은 인터뷰하지 않는다. "자료 요청" 목록으로 한 번에 받는다.

**기록**: 답을 받을 때마다 `material.md`에 원문 그대로 덧붙이고, `state.md`의 체크리스트를 갱신한다. 사용자만 쓰는 표현에는 `★`를 붙인다. 서너 번 주고받을 때마다 진행 상황을 한 줄로 보여 준다(`문항 1: ☑ 계기 ☑ 해 본 것 ☐ 왜 여기`).

**막힐 때**: 다른 각도에서 묻는다. 그래도 막히면 상황 예시를 두세 개 준다. 답의 예시가 아니라 떠올릴 상황의 예시다. 정말 없으면 그 재료 없이 쓸 방법을 찾는다(예: "아직 안 해 봤지만 이렇게 알아봤다"). 지어내지 않는다.

**멈출 때**: 체크리스트가 채워지면 멈춘다. 문항당 질문은 6개 안팎을 목표로 한다. 10개를 넘기면 "이 정도로 써 볼까요, 더 얘기할까요?"라고 묻는다. 선택 문항은 재료가 있으면 쓰자고 제안하고 사용자가 정한다.

빠른 모드: 문항당 질문 3~4개. 계기 장면과 핵심 이유만 확보한다.

## 4단계: 뼈대

`outline.md`에 문항별로 쓴다.
- **한 줄 요지**: 심사위원이 이것 하나만 기억하면 되는 문장
- **구성**: 3~5줄
- **쓸 재료**: `material.md`의 어느 답인지
- **평가 포인트 대응**: 어느 재료가 어느 평가 포인트에 답하는지
- **약한 곳**: 근거가 부족한 부분

요지를 잡을 때는 짐작을 먼저 내놓아도 된다("제가 보기엔 요지가 A 같은데 맞아요?").

모든 문항을 한 번에 보여 주고 **사용자의 명시적인 답("좋아", "응", 수정 요청)을 받은 뒤에** 초안을 쓴다. 답이 없으면 기다린다. 승인을 `state.md`에 기록한다.

빠른 모드: 뼈대와 초안을 한 번에 보여 주고 함께 확인받는다.

## 5단계: 초안

- **무엇을 지어내면 안 되는가**: 사실, 경험, 수치, 감정, 판단, 각오는 `material.md`에 근거가 있어야 한다. 근거가 없는데 필요하면 사용자에게 묻는다. 연결어, 문장 순서, 문단 구성은 모델이 해도 된다.
- `★` 표현을 살린다. `~/.claude/write-with-me/voice.md`가 있으면 먼저 읽고 반영한다.
- 첫 문장, 분량, 상투어 규칙은 `references/checklist.md`가 기준이다.
- 글자 수는 `python3 <skill-dir>/scripts/count.py draft/q1.md --limit <분량> [--no-spaces]`로 센다. 공고가 공백 제외 기준이면 `--no-spaces`를 붙인다. 눈대중으로 세지 않는다.
- 문체는 공고 분위기를 따른다.

## 6단계: 블라인드 심사

`references/judges.md`를 따른다. 요점:
1. `review/pack.md`를 만든다. 공고의 공개 정보, 문항, 지원서 전체만 넣는다. **`material.md`, 인터뷰 기록, 조사의 "연결고리"는 넣지 않는다.** 실제 심사위원이 가진 정보만 준다.
2. **Claude 심사위원 3명**(sonnet)을 한 메시지에서 병렬로 띄운다. 페르소나는 `judges.md`의 1·2·3번이다. 서로의 결과를 보지 않는다.
3. `config.md`에서 외부 심사위원을 켰으면 같은 메시지에서 `scripts/run_judge.sh`를 Bash 백그라운드로 실행한다. Codex와 Antigravity가 각각 한 명씩이다. 외부로 보내는 pack에서는 이름과 연락처를 가린다.
4. 결과가 다 오면 메인이 `review/summary.md`로 취합해 보여 준다. 점수표, **두 명 이상이 지적한 것**을 먼저 보여 주고, 다음으로 이 단계의 핵심 심사자가 지적한 것, 의견이 갈린 것을 보여 준다.

빠른 모드: Claude 심사위원 1명(이 단계 핵심 심사자 페르소나)만 띄운다.

**수정 루프**:
- 심사에서 "궁금하다", "근거가 없다"가 나온 곳은 **3단계로 돌아가 그것만 묻는다.** 답은 `material.md`에 덧붙인다. 요지가 바뀌지 않으면 뼈대를 다시 확인받지 않는다.
- 고친 뒤 재심사는 사용자가 원할 때만 한다. **가장 낮은 점수를 준 페르소나 1명**만 새 에이전트(sonnet)로 띄운다. 심사는 최대 2라운드다. `state.md`에 라운드를 기록한다.
- AI 티 점검은 `checklist.md` B절(메인)과 심사위원의 7번 항목으로 충분하다. `humanize-korean` skill은 사용자가 원할 때만 마지막에 돌린다.

## 7단계: 마무리

`final.md`에 다음을 정리한다.
- 문항별 최종본과 글자 수(`count.py`)
- **제출 전 확인**: 회사·프로그램 이름 오타, 다른 지원서에서 남은 회사 이름, 문항 순서, 분량 기준, 마감 시각
- **예상 면접 질문 3개**: 심사위원 6번 답변을 모아 고른다. 빠른 모드에서는 생략한다.

제출은 사용자가 직접 한다.

## 8단계: 문체 메모

사용자가 고친 것 중 **취향**("나 이런 표현 안 써", "문장 더 짧게")은 `~/.claude/write-with-me/voice.md`에 한 줄로 추가하고 "다음에도 이렇게 할게요"라고 알린다. 이번 글에만 해당하는 수정은 적지 않는다. 새 규칙이 기존 규칙과 부딪히면 기존 줄을 고친다. 사용자가 지우라고 하면 지운다.

## 하지 않는 것

- 사용자 대신 경험을 만들어 내지 않는다. 면접에서 설명할 수 없는 문장은 해가 된다.
- 조사 결과로 회사 칭찬을 늘어놓지 않는다. 사용자 경험과 맞닿는 사실 하나만 쓴다.
- 실존 심사위원의 이름으로 그 사람을 흉내 내지 않는다. 배경과 역할만 페르소나로 쓴다.
- 0단계 시작 정보, 2-3 경험 목록, 자료 요청을 빼고는 질문을 여러 개 한 번에 던지지 않는다.
- 사용자 확인 없이 제출하거나 외부에 게시하지 않는다. 외부 심사위원은 사용자가 0단계에서 켠 경우에만 쓴다.
